Who & what is involved

Four players drive the run. The operator never talks to MAGIQ directly — the app holds two authentication tickets and does the work on their behalf.

🧑‍💼

Operator

MAGIQ system admin or power user. Signs in, reviews folders, and authorises deletion & purge.

🗓️

Records manager

Sets the specified cutoff date (e.g. Madhuri) inside MAGIQ Documents — the year-end line.

⚙️

DLC application

.NET API + React SPA + Hangfire engine. Runs the pipeline, tracks state, reports live progress.

🗄️

MAGIQ Documents

The source system. Reached via direct SQL (queries) and the srv.asmx SOAP API (operations).

Login — the two-ticket model

At sign-in the app calls AuthenticateUser twice, getting two independent tickets. This decouples the operator's screen from the long-running job, so logging out never kills a run in progress. Access is limited to an admin allowlist.

UI UI session ticket

Backs the operator's browser session. Not persisted. If the app restarts, the operator simply signs in again. Sliding 20-minute timeout, refreshed on each call.

PROC Process ticket

Dedicated to the background pipeline. Persisted in the app DB against the CleanupRun, so it survives an IIS recycle. A heartbeat keeps its 20-min window open during lulls; if it ever expires, the app silently re-obtains one — no manual re-auth.

The pipeline, step by step

Data flows top to bottom. Diamonds mark where the run branches on a rule or an operator decision.

1

Retrieve candidate documents

Automated · SQL

Run the pre-configured SQL query against MAGIQ Documents for every document whose modification date ≤ the specified cutoff. The query lives in appsettings.json, so it changes with the schema without a redeploy.

Cutoff: ≤ calendar year-endVolume: tens of thousandsSource: direct SQL / Dapper
2

Apply the Document Register query

Automated · SQL

Enrich the candidate set using the existing Document Register report query as the base. No extra fields are needed — the output is exactly what the query returns.

Config-driven · appsettings.jsonPhase 1 complete → candidate list ready
4

Produce candidate folders

Phase 2

From the candidate documents, derive every containing folder. This is where the protection rule bites: any folder holding even one document newer than the cutoff is protected — and so is its entire ancestor chain up the tree.

Rule 2 · full ancestor protectionEmpty parents may cascade-delete
🛡️
▲ Folder has a newer doc

Protected. The folder and every ancestor above it are locked and retained — maximum protection.

▼ All docs ≤ cutoff

Eligible. Folder stays a deletion candidate and moves forward to review.

5

Resolve full folder paths

Automated · SQL

Using the folder IDs from Step 4, run the configured path query to get human-readable full paths. These feed straight into the review screen.

Config-driven · appsettings.json
6

Review & select folders

Interactive · React

The operator sees every candidate folder in a virtual-scrolling table and chooses what to delete or keep. Folders whose names match the acronym list are pre-selected, but the operator can deliberately override an individual folder to keep it. Protected folders (Rule 2) are never selectable.

Columns: path · docs · folders · sizeFree-text filter☑ Pre-selected = acronym match
7

Confirm selections & archive choices

Interactive · React

Confirming submits the selections and captures the archive choices — it does not delete anything yet (that's Step 11). Before advancing, the system validates every selected folder against the delete constraint: any protected folder is flagged inline and blocks the run until deselected. An optional checkbox here can pre-authorise the final purge.

Explicit approval requiredBack-nav to Step 6 allowed☑ Optional: auto-proceed to purge
⛔
▲ Any folder still protected

Run halts. Blocking rows are shown inline — no deletion proceeds until they're resolved or deselected.

▼ All selected folders clear

Constraint satisfied. Operator confirms and the run advances to name normalization, then archival.

8

Normalize source names

Background · SOAP

Works around a MAGIQ bug: the desktop UI lets a document or folder be named with a double space, but the SOAP Move / CreateFolder ops collapse whitespace and can't move such an item. Before archiving, this phase renames the offending source items in place — folder levels first (top-down), then documents — via UpdateFolderProperties / UpdateDocumentProperties, collapsing each run of whitespace to a single space.

Every rename recorded (audit)⚠ Once begun, the run can't be deleted — only archivedIdempotent · resume-safe
9

Select or create the archive library

Interactive · SOAP

In a modal, the operator picks a destination: create a new library (prefilled Archive NATA - Dec 2024) or choose an existing one — optionally with a subfolder. Creation uses the SOAP CreateDomain operation.

Prefill: Archive {Library} - {Date}On-demand subfolder browsing
10

Move documents to the archive

Background · Hangfire + SignalR

Every candidate document is moved into the archive library in batches via SOAP Move. Live progress streams to the job details view; the dashboard polls every 30s. No rollback — failed docs are recorded, the rest continue, and the run returns to the failures afterward.

% bar · count · path · ETAFailures surfaced liveResume from point of failure
11

Delete empty folders

Background · SOAP

Once all moves in Step 10 are confirmed complete, folders left empty are removed via SOAP DeleteFolder. This step cannot start early.

Gate: Step 10 fully completeSame progress display as Step 10
🔑
Path A · Pre-authorised in Step 7

Purge proceeds automatically. The Step 7 username + timestamp are recorded as the authorisation.

Path B · Manual (default)

Dashboard shows “Ready for purge.” Operator opens the red Purge button and types permanently delete to confirm.

12

Delete & purge the archive library

Background · SOAP

After authorisation, a three-call sequence permanently removes the library: DeleteDomain sends it to the recycle bin → GetRecycleBinContent lists the items → PurgeRecycleBinItem wipes each one. No holding period — purge starts immediately, and user + timestamp are logged.

Run lifecycle & recovery

Every execution is one CleanupRun state machine. Only one run may be active at a time. Background phases are resumable — there is no rollback, only resume.

NotStarted

Run created; Phase 1 not yet triggered.

Running

A background phase is actively executing.

AwaitingInput

Paused at an interactive step; operator action required.

Failed

Unrecoverable error halted the run; recovery needed.

Cancelled

Operator cancelled mid-phase. Cannot resume — start a new run.

Completed

All phases finished. Final — a new year needs a new run.

Abandoned

Operator wrote off a failed run; unblocks a new one.

Reset

Restart the current phase from the beginning.

Retry

Resume the current phase from the point of failure, skipping completed work.

Abandon

Mark the run Abandoned (simple confirm) and unblock a new run.

The five governing rules

Everything the pipeline does reduces to these. They're what make an automated bulk delete safe.

1 · Date cutoff

Documents modified on or before the specified year-end date are deletion candidates.

2 · Folder protection

A folder with any newer document is retained — and so is its full ancestor hierarchy.

3 · Empty folders

Folders left empty after the cull must be deleted.

4 · Delete constraint

No deletion runs while any selected folder is protected. Validate all first; report blockers.

5 · Confirm before purge

The archive library is never purged without authorisation — pre-granted or typed — with user + timestamp logged.
