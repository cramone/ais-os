# Spec Coherence Review — magiq-media

You are a Principal Software Architect auditing a DDD/CQRS/event-sourced specification for
**internal coherence**. Your job is to find everything in `docs/spec/` that is broken, missing,
half-designed, incomplete, or does not make sense — and to argue each finding with evidence.

Do not assume the specification is correct. It has been remediated across nine phases and every
automated check returns zero; that is exactly why the remaining defects are the ones no check can
see. A green run proves the guard ran. It does not prove the tree is clean.

## What counts as a finding

Nine kinds. Each is a real shape this tree has produced before, so none of them is hypothetical.

### 1. Contradiction — two files state incompatible things

The highest-value finding and the hardest to see, because it requires holding two files at once.
*Shape seen before:* one context overview disowned retention entirely while that aggregate's write
model specified retention periods and an erasure command.

When you find one, **say which side you believe and why** — the review that only reports "these
disagree" has done half the work.

### 2. A rule with no carrier

A behaviour is specified in terms of a member, flag, field or parameter that nothing in the tree
declares. The rule reads as normative and cannot execute.
*Shape seen before:* precedence rules for a deprecated snapshot field, where neither the compiled
field nor the snapshot field carried the flag those rules read.

### 3. A pointer that no longer resolves — or resolves to the opposite

Not a broken link (the guard catches those). A live cross-reference whose target has since been
rewritten to say something else, or that promises a section content the target does not contain.
*Shape seen before:* a warning that cited a `§ Service Boundaries` which by then stated the
opposite of the claim citing it.

### 4. A half-designed path

The pieces of a flow exist but the flow does not close:
- a command with no event, or an event no projector consumes
- an endpoint with no `## Authorization` row, or a permission not in the vocabulary
- an error code in an aggregate's prose but absent from `shared/error-catalog.md`, or a catalogue
  row for a code nothing raises
- a field with a declared type and no validation rule, or a constraint with no refusal code
- a DTO member referenced in prose but missing from the record declaration
- an integration event with a publisher and no consumer, or a consumer for an event nobody publishes

### 5. An unresolved either/or

Prose that names two options and picks neither — "either carry them through both DTOs or drop them
from the value object". A specification that poses a question is a specification with a hole in it.
Open questions belong in `plans/`, not in `docs/spec/`.

### 6. A quantity stated twice, differently

Two caps, two limits, two counts, two retention periods, two timeouts for the same thing in two
places. Also: a number stated in prose that disagrees with the same number in a table, a diagram, or
an example payload.

### 7. An inventory or enumeration that does not match itself

Aggregate lists, status enums, capability lists, role lists, queue lists, event lists — anywhere the
tree enumerates a closed set more than once. Compare every statement of the same set.

### 8. A state machine that does not hold

An unreachable state; a terminal state with an outbound transition; a transition with no command
behind it; a status the read model cannot represent; two files drawing the same lifecycle
differently.

### 9. Incomprehensible or self-undermining prose

A rule you cannot act on after reading it three times. A sentence that asserts and then withdraws
the assertion. A definition that defines a term with itself. A paragraph whose subject changes
mid-way. These are real defects — a specification nobody can follow does not specify anything — but
hold yourself to a high bar and quote the passage in full so the judgement is reviewable.

## What is NOT a finding

This tree has been swept repeatedly. Most of what looks like residue is load-bearing, and a review
that reports it will bury its own signal.

- **`⚠` markers.** There are ~179 and they stay. They are durable design caveats and hazards, and
  `README.md` row 14 documents the convention — they are the contested-rule register. A warning
  marker is a finding only if what it *says* is wrong, stale, or contradicts its own section.
- **Domain vocabulary that reads like process language.** `retired`, `superseded`, `deprecated`,
  `deferred`, `no longer`, `still open`, `unresolved` are all real domain terms here —
  `RetiredFieldDefinitions`, `SupersededBy`, deprecated fields, a standalone upload's processing
  quota deferred to assign time, a change request still open. **Read the sentence before you judge
  the word.**
- **`§ Deliberately not supported` sections.** Stated absences are a feature. An absence is a
  finding only if it contradicts something the tree elsewhere claims exists.
- **`<agg>.design-decisions.md` carrying rationale.** A standing, documented exception.
- **`recordtype-diagrams.html`.** A derived rendering that says so. Where it disagrees with the
  spec, the spec wins — so a disagreement is a finding against the HTML, filed as low severity.
- **Style, tone, formatting, heading casing.** Not this review.

## Method

The tree is too large for one pass. Partition it, fan out, then reconcile centrally — the
cross-cutting findings only appear in the reconcile step, so do not skip it.

**Step 1 — Inventory before you judge anything.**
List every `.md` under `docs/spec/` with its line count, grouped by bounded context. Write the
totals down. **Survey before you count**: every time this workstream predicted a number before
measuring it, the prediction was wrong in both directions.

**Step 2 — Fan out, one subagent per bounded context.**
Contexts: `AssetManagement`, `Catalog`, `ChangeRequests`, `Metadata`, `Processing`, `Registration`,
`DocumentSigning`. Each subagent reads that context's `context-overview.md`, every aggregate's
`*.write-model.md` / `*.read-model.md` / `*.api.md` / `*.scenarios.md`, and any saga file, and
applies the nine kinds above **within** that context.

Give every subagent the evidence contract below verbatim. Require findings back, not file dumps —
the agent's conclusion is what reaches you, and a subagent that returns prose summaries of files has
wasted its budget.

**Step 3 — The cross-cutting pass, which you do yourself.**
`shared/` and `architecture/` are where contradictions between contexts live, and no per-context
subagent can see them. Read `shared/error-catalog.md`, `shared/api-conventions.md`,
`shared/api-permissions.md`, `shared/cross-aggregate-invariants.md`, `shared/cascade-rules.md`,
`shared/consistency-model.md`, `shared/event-store-and-messaging.md`, `shared/operations.md`,
`glossary.md`, and `architecture/*.md` against each other and against what the subagents returned.

Then run these specific reconciliations, which are the ones that have historically failed:
- every error code in `error-catalog.md` ↔ every aggregate that raises one
- every route in each `<agg>.api.md` ↔ its `## Authorization` row ↔ the `api-permissions.md` vocabulary
- every aggregate inventory statement across `domain-model.md`, `bounded-contexts.md` and the seven
  context overviews
- every `glossary.md` term ↔ how that term is used in the contexts
- every `README.md` map row ↔ what its named file actually contains today

**Step 4 — Reconcile, dedupe, rank.**
The same defect will arrive from two subagents wearing different names. Merge them. Rank by blast
radius: a contradiction that would send two engineers in opposite directions outranks a dangling
pointer.

## The evidence contract

Every finding, from you or from a subagent, must carry all of this. A finding that cannot fill these
fields is not ready to report.

```
ID          SC-nnn
Severity    high | medium | low
Kind        one of the nine
Claim       one sentence: what is wrong
Evidence    file:line for EVERY side of it, each with a verbatim quote
Checked     what you compared it against, named explicitly
Why         why this is wrong, not merely that two things differ
Ruling      if it needs Chase to decide: the single smallest question, with the options
            and the consequence of each. Otherwise: the correction you would propose.
```

Two hard rules on evidence:

- **Quote, do not paraphrase.** A paraphrase of a spec sentence is a new sentence, and this
  workstream has twice reported a defect that existed only in the paraphrase.
- **Read the whole surrounding section before quoting a line.** `docs_guard.py` skips fenced code
  blocks for a reason; so should your judgement. A line that reads as a contradiction often resolves
  three lines up.

## Traps — these are recorded failures, not hypotheticals

1. **Do not report a behaviour claim you could not settle from the documents.** Scope is
   spec-internal. "This flag is never read" is a claim about code. File it under § Could not settle,
   with the question stated precisely enough that someone can answer it in one look.
2. **A grep is a lead, not a finding.** Searching the *concept* returns noise at roughly twenty to
   one here: `retired|superseded|no longer|previously|used to` returns ~165 hits in `docs/spec`, of
   which almost all are domain vocabulary. Searching *phrasings with no domain reading* returned 8,
   of which 6 were real. Narrow to the phrasing, then read every hit.
3. **Do not trust a passing check as evidence of anything beyond itself.** The citations check
   returned a clean hard zero through seven phases because its pattern required a hyphen and could
   not match the ids that were actually present. The build-status check later failed the opposite
   way, matching a domain word and filling its baseline with false positives. Both were invisible
   from a green run.
4. **Count after you survey, never before.**
5. **When two documents disagree, work out which one owns the question** before deciding which is
   wrong. `README.md` names the owner for most questions; use it.
6. **Do not inflate the count.** A review reporting sixty findings where twelve are real is worse
   than one reporting twelve, because someone has to sort it. Fold duplicates; drop anything you
   cannot evidence.
