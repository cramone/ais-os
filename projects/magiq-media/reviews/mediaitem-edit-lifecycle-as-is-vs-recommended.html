MediaItem Edit Lifecycle — Design & Delivery Plan

Checkout, collaboration, revision and review. All open questions closed; §7 is the build order.

magiq-media · Catalog + ChangeRequests · ADO 34385 · decisions closed 2026-08-20 · verified against Catalog.Domain/Aggregates/MediaItems/MediaItem.cs @ develop

Decision record — closed 2026-08-20, Chase Ramone

Three questions were open in the review draft. All are now settled; this document is the design of record and supersedes the CR-first checkout model. An ADR carrying these decisions is step 0 of the plan in §7.

#QuestionDecisionConsequence
D1 Is a documented reason-for-change (or multi-item change) a requirement? Yes — Branch B. ChangeRequest becomes a long-lived container, not a comment thread. No rename to ReviewThread. CR keeps its name and gains a lifecycle independent of the lock. See §4.
D2 May an edit lock expire on its own? Configurable per profile. LeaseDurationMinutes nullable on MediaProfile; null = never expires. Honours logged decision #2 per-tenant while making stale locks solvable. Reaped by the existing TimeoutScanner.
D3 When are reviewers named? At submit — but the CR may be opened at checkout. Separates "this change is governed" (checkout, D1) from "these people must approve it" (submit). Recovers the intent CR-first was reaching for, without binding a CR's lifetime to a lock's.

D1 was recorded on Chase's authority rather than a written compliance ruling. If that later comes back "not required", Branch B is over-build rather than wrong — the CR container is additive and nothing else in the design depends on it.

1  As it is now

Shipping

Five states on one aggregate. Review decisions live inline on MediaItem. There is no concurrency control of any kind, and the one policy that was meant to provide it is declared but never read.

editable writes blocked live to readers terminal satellite / not enforced

1 ReviewSession owns the decisions

An embedded value object on MediaItem, created by RequestPublication when reviewerIds is non-empty. Holds Pending / Approved / Rejected / Withdrawn per reviewer. The ChangeRequest aggregate records nothing about the outcome — it is purely a comment space.

2 The write gate is status-only

Every metadata and asset mutation checks exactly two things: Status ∈ {Draft, Revising} and !IsArchived. No ownership check, no lock, no version precondition. Two editors on the same item both write Metadata.Draft and the later write silently wins per field.

3 Rejection from a revision cycle corrupts state

Apply(MediaItemRejected) sets Status = Draft unconditionally. Revise a Published item, submit, get rejected — the item is now Draft while CurrentVersionNumber and PublishedAt still describe a live published version. DiscardRevision requires Revising, so there is no longer any way back to a clean Published state. Withdraw has the same defect.

4 Revision isolation works well

This part is sound. BeginRevision copies Metadata.Current into Metadata.Draft; readers keep seeing v(n) for the whole cycle; approval promotes the draft and bumps to v(n+1). Worth keeping unchanged.

2  Recommended

Proposed

The state machine barely changes — that is the point. The fix is one field on ReviewSession, one nullable value object holding who may write, and an If-Match header. No new statuses and no saga. The ChangeRequest aggregate stays where it is and gains a lifecycle of its own (§4) rather than being fused to the lock.

changed vs. today editable writes blocked live to readers

1 ReviewSession.OriginStatus

One field, captured at RequestPublication, replayed on reject and withdraw. Rejecting a revision returns you to Revising with the draft intact and v(n) still live — which is what everyone assumes already happens. The edit session reopens with the same editors, so there is no window where a rejected item is editable but unlocked.

2 EditSession — one mechanism, two shapes

A nullable value object naming the set of principals who may write. Solo checkout is the degenerate case where that set has one member; collaboration is the same object with more names in it. Lease, renewal, release-on-publish and force-release are identical either way.

3 Decisions stay on MediaItem

"Cannot publish without approval" is a MediaItem invariant, so it must be enforced inside that aggregate's transaction. Moving decisions onto the CR converts a local invariant into a distributed one guarded by a saga — strictly weaker, for no gain. The CR carries the why; the decision stays here.

4 The lock does not replace versioning

The event store already does conditional writes on AggregateVersion; the version is simply never shown to the caller, so conflicts are invisible and resolve last-write-wins. Exposing it as If-Match costs almost nothing and is mandatory the moment a session has two editors.

3  The two flows

Proposed

Both scenarios, on the same EditSession. The interesting difference is not the checkout call — it is what happens on the third and fourth rows of the second flow.

Flow A — exclusive checkout

Editors = { alice }

Nobody but Alice can write. Publishing closes the session and releases the lock. A true mutual-exclusion guarantee.

Flow B — collaborative checkout

Editors = { alice, bob, carol }

The lock keeps everyone else out. It does not order the three of them against each other — that is what If-Match is for.

// Catalog.Domain/Aggregates/MediaItems/ValueObjects/EditSession.cs
public sealed record EditSession(
    EditSessionId              Id,
    MemberId                   OpenedBy,
    IReadOnlySet<MemberId>     Editors,          // always contains OpenedBy
    MediaItemStatus            OriginStatus,     // Draft | Revising — where to return on reject
    DateTimeOffset             OpenedAt,
    DateTimeOffset?            LeaseExpiresAt);  // null = never expires (per-profile)

private EditSession? _activeEditSession;

public bool CanWrite(MemberId actor) => _activeEditSession is null
    ? CheckoutPolicy != CheckoutPolicy.RequiredForEdit
    : _activeEditSession.Editors.Contains(actor);

Flow A — exclusive checkout, publish releases the lock

Editors = { alice }

Why publish, not check-in, is the natural release point

Submitting moves the item to PendingApproval, where writes are already blocked by status. Holding a lock on top of that would be two mechanisms guarding the same thing — and would leave you deciding who owns the lock while reviewers deliberate. Closing the session at submit means the lock exists only during the window it actually protects.

Flow B — collaborative checkout

Editors = { alice, bob, carol }

The part that bites — a shared lock is a membership test, not mutual exclusion

In Flow A the lock genuinely guarantees "no changes can be made." In Flow B that guarantee evaporates the moment the holder set exceeds one: Bob and Carol can still clobber each other, as rows 3–4 show. Ship collaborative checkout without If-Match underneath and you have built something that looks like it prevents conflicts and silently doesn't — worse than no lock at all, because people will trust it.

MechanismQuestion it answersFlow AFlow B
EditSessionAre you allowed in this room?Load-bearing — it is the whole featureLoad-bearing — keeps Dave out
If-Match / versionIs your copy current?Redundant but free — one editor can't conflict with themselvesLoad-bearing — the only thing ordering Bob against Carol

3.1  How we deal with it

three layers, ship one

You cannot make a shared lock exclusive — "shared" and "exclusive" are contradictory. So stop asking the lock to do that job. Three other moves are available: detect collisions precisely instead of coarsely, shrink the unit of exclusion until it is exclusive again, or prevent them socially before they reach the server. They layer, and only the first is needed now. 

// SetMetadataBatchHandler — on version mismatch only
var tail = new MediaItem(command.MediaItemId);
await eventStore.LoadAfterAsync(tenantId, tail, command.BaseVersion, ct);

var theirKeys = tail.KeysTouchedSinceLoad();              // fold over metadata events
var myKeys    = command.Fields.Select(f => f.FieldName).ToHashSet();

// rebase is opt-in per field and fails closed
var overlap  = myKeys.Intersect(theirKeys).ToHashSet();
var unsafeKeys = myKeys.Where(k => !mediaItem.SnapshotFields[k].AllowsConcurrentEdit);

return (overlap.Count > 0 || unsafeKeys.Any())
    ? DomainError.Conflict("VersionConflict", overlap.Union(unsafeKeys))
    : /* rebase */ mediaItem.SetMetadataBatch(command.Fields, baseVersion, ...);

3.2  Coupled fields — and how we deal with them

fail closed

The failure mode has a name: write skew

Carol reads StartDate = 1 Jan at v13 and sets EndDate = 31 Jan. Bob changes StartDate to 1 Mar at v14. The write sets are disjoint, so a naive rebase accepts — and Carol's value is now nonsense. This is textbook write skew under snapshot isolation, and the cause is precise: If-Match plus a write-set comparison captures what the caller wrote and ignores what the caller read.

The fix is to invert the declaration

Declaring dependency groups — the earlier proposal — asks the schema author to enumerate every coupling that exists. That is open-ended negative space, and the cost of forgetting one is silent data corruption. Declaring independence is a closed, positive assertion about one field, and the cost of forgetting one is a spurious 409. Same information, opposite failure mode. For regulated records there is only one defensible direction.

// Metadata.Domain/ValueObjects/FieldDefinition.cs — one flag, next to the ones already there
public sealed record FieldDefinition(
    FieldName FieldName,
    ...
    bool IsRequired,
    bool IsImmutable,
    bool IsSearchable,
    bool AllowsConcurrentEdit,   // NEW — defaults to false
    ...);

// Rebase is permitted only when BOTH hold:
//   1. myKeys ∩ theirKeys == ∅          (no one overwrote me)
//   2. every key in myKeys is AllowsConcurrentEdit  (my value depends on nothing else)

Condition 2 only has to hold for my write set, not theirs. If Notes is declared independent, then by definition no change Bob made can invalidate the value Carol computed for it — that is exactly what the flag asserts. Good candidates: notes, description, tags, keywords, free-text classification. Bad candidates: anything in a date range, anything participating in a total, anything with a "see also" relationship. Default false means an unconsidered field behaves exactly as it does with no rebase at all.

Make the rebase visible in the audit trail

A rebased write is still a write that landed against a version the caller never saw. Carry BaseVersion on MediaItemMetadataFieldSet and MediaItemMetadataBatchSet so the gap between "what they were looking at" and "what they wrote onto" is reconstructable from the stream. Two extra bytes on an event, and it is the difference between an auditor being able to explain a value and having to guess. Old events replay with BaseVersion = null, so this is non-breaking.

Sequencing

Layer 1 plus AllowsConcurrentEdit is the whole answer for now — a bounded change inside Catalog, built on a platform API that already exists, and the thing that makes collaborative checkout honest rather than decorative. Layers 2 and 3 are both "later, if the usage data says so." Shipping Flow B without layer 1 is the one outcome to avoid.

4  EditSession and ChangeRequest

Decided — Branch B

Are these the same idea wearing two hats? The overlap is real, and CR-first merging them was not arbitrary. They are nonetheless separate — and the reason is lifespan, not semantics. Decision: the ChangeRequest becomes a long-lived container holding many short lock episodes.

Three things that keep getting conflated

ConceptWhat it isNatural lifespanCardinality
The lockWho may write, right nowMinutes → hoursExactly one item
The change unitThis batch of edits as a nameable, justifiable thingDays → weeksOne or many items
The decisionApproved / rejected, and by whomOne submit cycleExactly one item

CR-first merges the first two, and puts the third on the CR as well. The EditSession design in §2–3 merges none of them — and that is its genuine weakness: nothing owns "the change" as a first-class object. It exists only implicitly, as Metadata.Draft plus the events between two published versions. There is nowhere to hang a title, a justification, or a conversation that survives a rejection.

If they are separate, this is how they relate

Not one-to-one. One long-lived change request containing many short lock episodes — which is what the lifespan mismatch forces.

Why merging them breaks — three mismatches

MismatchConsequence of merging
Lifespan decisive A lock must be short or it blocks everyone; a change request may live for weeks across review rounds. Merged, you either hold a lock for weeks or you kill the CR when the lock releases. This is precisely the awkwardness already visible in CR-first: CheckoutBound with no timeout, held indefinitely, with the TimeoutScanner deliberately not pointed at it.
Cardinality A lock is inherently per-item. A change request could reasonably cover forty records in a bulk reclassification. CR-first cannot express that at all.
Optionality Most edits want a lock and no CR. Some changes want a CR and no lock — "please reclassify these records" is a proposal someone else executes. Merged, that is inexpressible.

What gets built

AggregateChangeNotes
ChangeRequest Gains Title, Reason, Status: Open | Resolved | Abandoned, Scope: IReadOnlyList<MediaItemId>, ResolvedAt?. Keeps its existing comment thread untouched. Keeps its name — the earlier ReviewThread rename is withdrawn. It is not a state machine bound to a lock; it is a container with an open/closed lifecycle.
EditSession Gains nullable ChangeRequestId. A session may or may not sit inside a CR. Many sessions may reference the same CR over its life.
MediaProfile Gains ChangeRequestPolicy: None | RequiredForEdit. This is the compliance control. RequiredForEdit → checkout without a changeRequestId is rejected with ChangeRequestRequired. It delivers CR-first's actual goal without CR-first's coupling.
(no new orchestration) The client creates the CR, then checks out under it: POST /change-requests → POST /items/{id}/checkout { changeRequestId }. Two calls, no cross-module command, no saga. Catalog validates existence against the ChangeRequestReference index it already maintains.

Why this recovers what CR-first was reaching for

The motive behind CR-first was sound: don't let someone edit for an hour and only then discover the change is governed. ChangeRequestPolicy = RequiredForEdit delivers exactly that — you cannot open a lock on a governed profile without declaring the CR first. What it drops is the part that caused the trouble: the CR's lifetime is no longer the lock's lifetime, so a CR can outlive a rejection, span a second edit session, and close on its own terms. MediaItemCheckoutReviewSaga and its five consumers stay deleted — there is no longer anything to keep in step.

Scoped deferral — multi-item CRs

Scope is modelled as a list from day one but phase 1 only ever writes one entry, and a CR resolves when its single linked item publishes. Fan-out resolution across many items is deliberately not built. Trigger to revisit: the first real bulk-reclassification request from a tenant. Modelling the list now means that is an additive change, not a migration.

8  Net effect on the build

One value object, one nullable field, seven commands, an If-Match header and a range query on the conflict path — all inside Catalog. Against the CR-first plan this drops a saga, five integration-event consumers, two CR states and a cross-module command, while covering both scenarios and leaving the ChangeRequest aggregate exactly as it is today.

Where to start on Monday

Step 0 and step 1 in either order. The ADR because the decisions are fresh and cheapest to write down now; the OriginStatus fix because it is a single field, a two-line change to Apply(MediaItemRejected) and Apply(MediaItemWithdrawn), and it closes a defect that is live in develop today. Neither depends on anything else in this document.
