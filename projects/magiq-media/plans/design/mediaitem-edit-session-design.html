MediaItem Edit Session

One locking mechanism that serves both solo checkout and multi-party collaboration — and the concurrency guarantee that changes between them.

magiq-media · Catalog · design proposal · 2026-08-20 · supersedes the CR-first checkout model

Your two scenarios are not two features. They are one mechanism with a holder set of size 1 or N. An EditSession names who may write; solo checkout is the degenerate case where that set has one member. Everything else — lease, renewal, release-on-publish, force-release — is identical.

Scenario 1 — exclusive

Editors = { alice }

Nobody but Alice can write. Publish closes the session and releases the lock. This is a true mutual-exclusion guarantee.

Scenario 2 — collaborative

Editors = { alice, bob, carol }

The lock keeps everyone else out. It does not order the three of them against each other — that needs optimistic concurrency underneath.

1The model

One nullable value object on the aggregate. No new statuses, no second aggregate, no saga — the whole thing is local to MediaItem and enforced inside its own transaction. 

// Catalog.Domain/Aggregates/MediaItems/ValueObjects/EditSession.cs
public sealed record EditSession(
    EditSessionId              Id,
    MemberId                   OpenedBy,
    IReadOnlySet<MemberId>     Editors,          // always contains OpenedBy
    MediaItemStatus            OriginStatus,     // Draft | Revising — where to return on reject
    DateTimeOffset             OpenedAt,
    DateTimeOffset?            LeaseExpiresAt);  // null = never expires (per-profile)

// On the aggregate
private EditSession? _activeEditSession;
public bool IsCheckedOut => _activeEditSession is not null;
public bool CanWrite(MemberId actor) => _activeEditSession is null
    ? CheckoutPolicy != CheckoutPolicy.RequiredForEdit
    : _activeEditSession.Editors.Contains(actor);

2Scenario 1 — exclusive checkout, publish releases the lock

Alice takes the item, nobody else can touch it, publishing hands it back.

Why publish, not check-in, is the natural release point

Submitting moves the item to PendingApproval, where writes are already blocked by status. Holding a lock on top of that would be two mechanisms guarding the same thing — and would leave you deciding who owns the lock while three reviewers deliberate. Closing the session at submit means the lock exists only during the window it actually protects.

3Scenario 2 — collaborative checkout

Same session, larger holder set. Note rows 3 and 4: Bob gets in because he's an editor, Carol gets a 409 from a colleague — two different rejections that a single mechanism cannot produce.

4The part that bites

A shared lock is not mutual exclusion — it is a membership test

In scenario 1 the lock genuinely guarantees "no changes can be made." In scenario 2 that guarantee evaporates the moment the holder set exceeds one: Bob and Carol can still clobber each other. If you ship collaborative checkout without If-Match underneath it, you will have built something that looks like it prevents conflicts and silently doesn't — which is worse than no lock at all, because people will trust it.

The two mechanisms answer different questions and you need both:

MechanismQuestionScenario 1Scenario 2
EditSessionAre you allowed in this room?Load-bearing — it is the whole featureLoad-bearing — keeps Dave out
If-Match / versionIs your copy current?Redundant but free — one editor can't conflict with themselvesLoad-bearing — the only thing ordering Bob against Carol

How far to take collaboration

If-Match at the aggregate level means any two concurrent writes conflict, even to unrelated fields. That's correct but coarse — with three people editing, Carol will hit 409 a lot. Two ways to soften it, in increasing order of cost:

OptionBehaviourCost
Aggregate-level If-MatchAny concurrent write → 409, client re-reads and retries.Free — the event store already does this conditional write. Start here.
Field-level merge409 only when the same field changed. Server compares the changed key-set against events since the caller's base version.Moderate — needs a "changes since version N" read. Worth it if 409 rates get annoying in practice, not before.
Live co-editing (CRDT/OT)No conflicts, real-time cursors.Don't. It's a different product, and it fits poorly with an append-only audit trail for regulated records.

5Edge cases worth deciding now

SituationProposed behaviour
Initiator leaves the company mid-sessionAny remaining editor can continue and submit. The session belongs to the set, not to OpenedBy. Only ForceRelease needs elevated rights.
Last editor removed from the setReject — Editors must be non-empty. Use ForceRelease or AbandonCheckout to end a session.
Lease expires with unsaved draftSession closes, draft is kept. Expiry releases the lock, never the work. Next person to check out inherits the draft and sees who left it.
Reviewer rejects a submitted itemEditSessionReopened with the same editor set and a fresh lease, item returns to OriginStatus. Avoids a window where a rejected item is editable but unlocked.
Checkout on a Published itemImplicitly raises MediaItemRevisionStarted. One user action. OriginStatus = Revising is recorded on the session.
Active DocumentSigningSessionBlock checkout — SigningSessionInProgress. Reuses the guard already on RequestPublication.
Bulk metadata across many itemsBulk skips the session requirement, or fails per-item with MediaItemAlreadyCheckedOut in the existing BulkItemError shape. Recommend the latter — a bulk path that ignores locks makes the lock a lie.

6What this replaces

Everything below exists only in mediaitem.checkout-cr-saga.md and the ChangeRequests specs — none of it is implemented, so removing it costs nothing but a spec edit.

Net effect on the build

One value object, one nullable field, six commands, and an If-Match header — all inside Catalog. Against the CR-first plan this drops a saga, five integration-event consumers, two CR states, and a cross-module command, while covering both of your scenarios and leaving the ChangeRequest aggregate exactly as it is today.
